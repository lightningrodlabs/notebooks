# Comments on notes — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Google-Docs-style comments on notebook text in both editors, anchored by Automerge Text marks inside the note's Syn document.

**Architecture:** The Syn grammar's text moves from a list of characters to an Automerge Text so marks and cursors work; comments are records in the same document, their ranges are marks named `comment:<id>`. Pure modules under `ui/src/comments/` derive ranges, overlap segments, margin layout and export formats; a Lit reactive controller shared by both editors turns those into highlights and a `<comment-margin>` column.

**Tech Stack:** Lit 3, Automerge 3.4 (`splice`, `mark`, `marks`, `getCursor`), `@holochain-syn/core` 0.700 (`SliceStore.change`, `docState`, `ephemeral`), ProseMirror decorations, CodeMirror 5 `markText`, CSS Custom Highlight API, Vitest 3 at the repo root run through `nix develop`.

**Spec:** `docs/superpowers/specs/2026-10-15-comments-design.md`

## Global Constraints

- Run every npm/node/test command inside the flake shell: `nix develop --command <cmd>` (Node 24; the installed tree needs it).
- Tests: `nix develop --command ./node_modules/.bin/vitest run` from the repo root; test files sit beside their module as `*.test.ts` under `ui/src/`.
- Type check + lint: `nix develop --command npm run build -w ui` must stay clean (vite checker runs tsc and eslint).
- Commit messages: no `Co-Authored-By:` or "Generated with" trailers (user's global rule).
- The text stays markdown; comments are never written into `body`.
- Mark name format is exactly `comment:<id>`; value `true`; `expand: 'none'`.
- Old commits keep the legacy `text: string[]` shape forever: every read-only consumer goes through `textOf(state)`.
- Shoelace components are imported per component (`@shoelace-style/shoelace/dist/components/<c>/<c>.js`) as the codebase does.

## Review Focus

1. A legacy note opened by two peers at once: both migrate; afterwards text must be identical on both and no `text` list remains (Task 2 test "concurrent migration converges").
2. Deleting text that contains a whole comment: the record stays, the mark disappears, the card shows as orphan rather than crashing (Task 4 "orphan after full deletion", Task 6 model test).
3. Typing at the edge of a commented range must not extend it; typing inside must (Task 4 "expand none semantics").
4. Two comments on the same range from two peers: both survive a merge and the segments carry both ids (Task 4 "concurrent overlapping comments", Task 5 segments test).
5. A selection whose edge sits on a markdown syntax character in the rich-text editor: the comment must land on the nearest text character, never throw (Task 8 uses the existing clamp/fallback; manual check listed in Task 8).
